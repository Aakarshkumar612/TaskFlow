📋 1. Executive Summary

What is TASKFLOW?

TASKFLOW is a sophisticated project management platform that implements core features inspired by Asana's Work Graph® data model. It provides teams with powerful task tracking, multiple project views, workflow automation, and real-time collaboration capabilities. The system is designed as a modern full-stack application using React, Node.js/Express, PostgreSQL, and Docker - optimized for demonstrating enterprise-level architecture in technical interviews.

Core Value Propositions

🎯 Task & Project Management

  • Create, assign, and track tasks with rich metadata
  • Organize work into projects and sections
  • Multiple views: List, Board (Kanban), Timeline, Calendar
  • Subtasks, dependencies, and milestones

👥 Team Collaboration

  • Real-time updates via WebSockets
  • Comments and @mentions on tasks
  • File attachments and document sharing
  • Team workspaces and shared projects

⚡ Workflow Automation

  • Custom rules and triggers
  • Automated task assignments
  • Status change notifications
  • Template-based workflows

📊 Progress Tracking

  • Project timelines and Gantt charts
  • Task completion analytics
  • Team workload visualization
  • Custom dashboards and reports

🗄️ 4. Database Schema Design (PostgreSQL)

The database follows a relational model inspired by Asana's Work Graph® - where tasks, projects, and users are interconnected. All tables include created_at and updated_at timestamps with soft delete support via deleted_at.

⚡ 4.1 Database Indexes & Constraints (Production Ready)

These indexes and constraints are CRITICAL for production performance. PostgreSQL does NOT auto-index foreign keys. 

-- ==========================================
-- FOREIGN KEY INDEXES (PostgreSQL does NOT auto-create these)
-- ==========================================
CREATE INDEX idx_tasks_project_id ON tasks(project_id);
CREATE INDEX idx_tasks_section_id ON tasks(section_id);
CREATE INDEX idx_tasks_assignee_id ON tasks(assignee_id);
CREATE INDEX idx_tasks_creator_id ON tasks(creator_id);
CREATE INDEX idx_tasks_parent_task_id ON tasks(parent_task_id) WHERE parent_task_id IS NOT NULL;
CREATE INDEX idx_comments_task_id ON comments(task_id);
CREATE INDEX idx_comments_user_id ON comments(user_id);
CREATE INDEX idx_attachments_task_id ON attachments(task_id);
CREATE INDEX idx_notifications_user_id ON notifications(user_id);
CREATE INDEX idx_workflow_rules_project_id ON workflow_rules(project_id);
CREATE INDEX idx_team_members_team_id ON team_members(team_id);
CREATE INDEX idx_team_members_user_id ON team_members(user_id);
CREATE INDEX idx_project_members_project_id ON project_members(project_id);
CREATE INDEX idx_project_members_user_id ON project_members(user_id);
CREATE INDEX idx_sections_project_id ON sections(project_id);
CREATE INDEX idx_projects_team_id ON projects(team_id);
CREATE INDEX idx_projects_owner_id ON projects(owner_id);

-- ==========================================
-- COMPOSITE INDEXES (For common query patterns)
-- ==========================================
CREATE INDEX idx_tasks_assignee_status ON tasks(assignee_id, status);
CREATE INDEX idx_tasks_project_status ON tasks(project_id, status);
CREATE INDEX idx_tasks_due_date ON tasks(due_date) WHERE due_date IS NOT NULL;
CREATE INDEX idx_notifications_user_read ON notifications(user_id, is_read);
CREATE INDEX idx_comments_task_created ON comments(task_id, created_at DESC);

-- ==========================================
-- GIN INDEXES (For JSONB and Array columns)
-- ==========================================
CREATE INDEX idx_tasks_custom_fields_gin ON tasks USING GIN(custom_fields);
CREATE INDEX idx_tasks_tags_gin ON tasks USING GIN(tags);
CREATE INDEX idx_notifications_metadata_gin ON notifications USING GIN(metadata);
CREATE INDEX idx_workflow_trigger_conditions_gin ON workflow_rules USING GIN(trigger_conditions);

-- ==========================================
-- UNIQUE CONSTRAINTS (Prevent duplicate entries)
-- ==========================================
ALTER TABLE team_members ADD CONSTRAINT uk_team_user UNIQUE(team_id, user_id);
ALTER TABLE project_members ADD CONSTRAINT uk_project_user UNIQUE(project_id, user_id);
ALTER TABLE task_dependencies ADD CONSTRAINT uk_task_dependency UNIQUE(task_id, depends_on_task_id);

-- ==========================================
-- CHECK CONSTRAINTS (Data integrity)
-- ==========================================
ALTER TABLE task_dependencies 
  ADD CONSTRAINT chk_no_self_dependency CHECK (task_id != depends_on_task_id);

ALTER TABLE notifications 
  ADD CONSTRAINT chk_valid_entity_type 
  CHECK (related_entity_type IN ('task', 'project', 'comment', 'team'));

-- ==========================================
-- ON DELETE BEHAVIORS (Must be defined in Prisma schema)
-- ==========================================
/*
tasks.assignee_id → ON DELETE SET NULL (task survives user deletion)
tasks.creator_id → ON DELETE SET NULL
tasks.parent_task_id → ON DELETE CASCADE (delete subtasks with parent)
comments.user_id → ON DELETE SET NULL (show "deleted user" for comments)
attachments.uploaded_by → ON DELETE SET NULL
project_members → ON DELETE CASCADE (remove membership when user deleted)
team_members → ON DELETE CASCADE
*/

⚠️ Critical Production Notes

🔴 TIMESTAMPTZ not TIMESTAMP: All timestamp fields use TIMESTAMPTZ to handle timezones correctly

🔴 UNIQUE on junction tables: team_members(team_id, user_id) prevents duplicate memberships

🔴 FK indexes required: PostgreSQL does NOT auto-index foreign keys - must create manually

🔴 ON DELETE rules: Must be explicitly defined to prevent orphaned records

🔴 GIN indexes on JSONB: Required for efficient JSON field queries

⭐ 10. Key Features Implementation Strategy

📋 Multiple Project Views

Implement different ways to visualize project tasks:

  • List View: Table format with sorting, filtering, grouping
  • Board View: Kanban-style columns by status/section using drag & drop
  • Timeline View: Gantt chart showing task durations and dependencies
  • Calendar View: Monthly calendar with tasks on due dates

Implementation: Each view is a separate React component consuming the same task data but rendering differently. Use react-beautiful-dnd for board view drag-drop.

🔄 Real-Time Collaboration

Live updates when multiple users work on same project:

  • WebSocket connections via Socket.IO
  • Task changes broadcast to all viewers
  • Comment notifications in real-time
  • User presence indicators (online/typing)
  • Optimistic UI updates for instant feedback

Implementation: Socket.IO rooms per project. Emit events on task CRUD. Use Redux for state sync. Optimistic updates with rollback on error.

⚡ Workflow Automation

  • Rule builder UI (IF this THEN that)
  • Trigger events: task created, status changed, etc.
  • Actions: assign, move, comment, notify
  • JSONB storage for flexible rule configs
  • Event-driven execution via middleware

🔐 Authentication & Authorization

  • JWT-based auth with refresh tokens
  • Role-based access control (RBAC)
  • Project-level permissions (admin/member/viewer)
  • Protected routes with guards

🔄 11. Real-Time Task Update Flow (Sequence)

Scenario: User A updates a task, User B sees it in real-time

1
User A edits task title in React UI

User changes task title in task detail panel and clicks "Save"

2
Frontend sends PUT request to API

React → PUT /api/v1/tasks/:id with { title: "New Title" }

3
Backend validates & updates database

Express validates input → Prisma updates PostgreSQL → returns updated task

4
Socket.IO emits task:updated event

Backend emits to all users in project room via Socket.IO + Redis adapter

5
User B's frontend receives update

Socket.IO client on User B's browser receives task:updated event

6
Redux store updates automatically

React Query invalidates cache → Redux dispatches update → UI re-renders with new title

7
Notification created for task assignee

If assignee ≠ editor, notification service creates alert → pushed via WebSocket

🔒 12. Security & Best Practices

🛡️ Authentication Security

  • • Password hashing with bcrypt (cost factor 12)
  • • JWT tokens with short expiry (15min access, 7d refresh)
  • • Refresh token rotation
  • • Token blacklist in Redis on logout

🔐 Authorization

  • • Role-based access control (RBAC)
  • • Project membership verification
  • • Middleware checks on every route
  • • Resource ownership validation

📝 Input Validation

  • • Joi/Zod schema validation on all inputs
  • • SQL injection prevention via Prisma ORM
  • • XSS protection via React escaping
  • • File type validation on uploads

🌐 Network Security

  • • HTTPS/TLS in production
  • • Helmet.js security headers
  • • CORS whitelist for allowed origins
  • • Rate limiting (100 req/15min per IP)

📊 Error Handling

  • • Global error handler middleware
  • • Structured error responses
  • • No sensitive data in error messages
  • • Winston logging for debugging

💾 Data Protection

  • • Database credentials via environment variables
  • • Prisma parameterized queries
  • • Soft deletes for data recovery
  • • Regular database backups
